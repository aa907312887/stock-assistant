# 调研结论：手动模拟交易

**日期**: 2026-06-06 | **规格**: [spec.md](./spec.md)

## 1. 持久化方案

- **决策**：MySQL 新建 2 张独立表（`manual_trading_session`、`manual_trading_operation`），与 `paper_trading_*` **完全隔离**。
- **理由**：规格要求落盘、比例跟盘、无股数；020 表结构围绕 FIFO/T+1/股数设计，复用成本高且易混淆。
- **备选**：单表 JSON 存流水——查询复盘与索引不便，放弃。

## 2. 用户隔离

- **决策**：会话表增加 `user_id`，所有 API 使用 `Depends(get_current_user)`，读写均过滤当前用户。
- **理由**：规格明确「登录用户维度」；个人持仓（`/api/portfolio`）已采用相同模式。
- **备选**：与 020 一样不做用户隔离——不符合规格，放弃。

## 3. 推进后待录价状态

- **决策**：会话增加 `awaiting_reval`（布尔）与 `pending_reval_date`（DATE，可选冗余）；用户点击快捷推进后日期先变更并置 `awaiting_reval=true`，**禁止**再次买入/推进，直至 POST 录价完成。
- **理由**：规格默认「推进后须录入收盘价」；显式状态机可避免并发误操作。
- **备选**：前端-only 禁用按钮——刷新后丢失约束，放弃。

## 4. 比例跟盘计算位置

- **决策**：**后端** `manual_trading_service` 使用 `Decimal` 计算；公式 \(V' = V \times P_{new}/P_{old}\)，买入时 `position_value += amount`、`total_invested += amount`。
- **理由**：落盘数据以服务端为准；与 020 一致由后端保证口径。
- **备选**：前端计算再提交——易被篡改且不利于测试，放弃。

## 5. 参考价（reference_price）锚定

- **决策**：
  - 首笔**买入**时若 `reference_price` 为空，设为该笔成交价；
  - **估值推进**录价后更新为录入的收盘价；
  - 同模拟日内多笔买入**仅累加金额**，不改变参考价（直至下次录价）。
- **理由**：比例调整只在「推进+录价」时发生；日内多次买入符合规格「允许多笔买入累加」。
- **备选**：每笔买入都重置参考价——与「推进后录收盘价」叙事不一致，放弃。

## 6. 日期快捷推进

- **决策**：后端使用 `datetime.date` + `relativedelta`（`python-dateutil`，项目已有）：
  - `day` → +1 天
  - `week` → +7 天
  - `month` → +1 月
  - `year` → +1 年
- **理由**：规格要求四档快捷推进；`relativedelta` 可正确处理月末（如 1-31 +1 月）。
- **备选**：仅支持固定 timedelta——月份/年不准确，放弃。

## 7. 前端页面形态

- **决策**：两页结构——列表/新建页 + 会话详情页（与 020 路由模式类似但**无全屏 K 线**）：
  - `/backtest/manual-trading`：会话列表、新建对话框
  - `/backtest/manual-trading/:sessionId`：操作区（买入、推进、录价、结束）、汇总卡片、流水表
- **理由**：需断点续作与多会话管理；单页塞全部功能不利于复盘已结束会话。
- **备选**：单页无路由——多会话切换体验差，放弃。

## 8. 定时任务

- **决策**：**不涉及**定时任务；纯用户触发 CRUD。
- **理由**：无行情同步、无批处理需求。

## 9. 鉴权与 020 差异说明

- **决策**：本功能 API **强制 JWT**；020 `/api/paper-trading` 保持现状（历史实现无 user_id），两者互不影响。
- **理由**：规格要求未登录不可访问；新功能从设计起绑定用户。
